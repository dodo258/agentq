# agentq 2 设计

一句话：你说一句需求，它带一个小队做到合进主分支，告诉你怎么看。它不是调度器：不管排队、名额和优先级，只管把一件事从头交接到尾。

## 为什么重做（2026-11-26）

用户：「太复杂了」说了三遍；「一个调度器做得跟一个操作系统一样真的有用吗？」「要的就是简单粗暴高效直接」。

旧版最近 7 天的数据：

- 产品代码 10-10 是 1,700 行，现在 48,110 行、28 个模块。
- 合并的 183 条，从开工到最后一次进门平均 76 分钟，干活 38 分钟，其余在过门、退回、等续跑。
- 过门 293 次退回 106 次。抽看 45 条退回理由，多数是几个少见条件凑齐才出的边角。审查提示词明写「概率低、每次影响小……都不能写成 note」。
- 324 次任务里 286 次由调度器自己挑起来（含会话写进待办的）；建议 24 小时没回就自动开工。
- 13% 的额度花在 agentq 改自己。

## 参照

- yetone 的 magpie（2026-10-09 看过作者的 X 和仓库）：多个会话同时做，agent 自己测自己合，CI 绿就发，每晚回看一次当天提交写教训。没有给每个改动排一串门。
- 小新指北 https://www.xiaoxin666.cn/#flow（用户多次点名）：主控拆任务书，每份写清范围、红线和唯一的交付；交回的是文件，不是结论；没看过聊天记录的独立模型只拿成品挑错，问题退回对应的人；同一批文件同一时间只交给一个 AI；技术检查通过不等于成品接受，最后由人看；每周列出从工作流里删了什么。
- Ralph loop：一个循环、一份任务文件、干净上下文，够用。

## 一条直线

```
一句话 ─→ 产品经理 ─→ 按模块同时做 ─→ 合到一起跑测试 ─→ 审计一次 ─→ 修一次 ─→ 合进主分支 ─→ 告诉你
小改动 ─→ 产品经理 ─→ 一个会话做完 ─→ 跑测试 ─→ 合进主分支 ─→ 告诉你
```

1. **产品经理**：一个会话。看项目、联网看同类和抱怨，写方案，划模块、定接口和验收。小改动不调研。不问人。
2. **做**：每个模块一个会话、一个 worktree，没有依赖的同时开工，不限个数。每个模块只动自己的目录，接口在方案里先定好。
3. **合**：做完就合进这条需求自己的分支。冲突让做这个模块的会话自己解决。
4. **测试**：都合完跑一次项目的 `.agentq/verify`。红了修，Opus 最多 3 次；还红请 Fable 出手一次。
5. **审计**：整个需求只审一次，交给 Codex 最强的模型、超高强度：和写代码的不是一家，看得到自家看不到的（没装、没额度就换 Claude 审）。它没看过方案和过程，只拿用户原话和成品，像用户那样走一遍，只找大 bug，写清在哪个模块。小改动不审。
6. **修**：一个会话先逐条核对，成立的全修掉，再跑一次测试。不再审。教训写进项目 `LESSONS.md`。
7. **交付**：主分支动过就先合进来，待办打勾；动过内容就再跑一次测试，测过的才合进主分支，推一条消息：做了什么、怎么看。

全程记一张交接单（`agentq log <编号>`）：谁接到什么、交回什么、在哪一步被打回。

做好不等于你接受：你看过成品，再说一句要改什么，又是一条新的需求。

停下来找人只有三种：Fable 出手也没修好；冲突解不了；需求要花钱、发布、删数据、用账号。

## 靠文件，不靠记忆

规矩和定过的事都落在文件里，换哪个会话、哪个模型都照着做：选型和模块化规范编译在程序里；大活的方案写进项目 `docs/specs/`；大项目分期，后面几期写进 `docs/BACKLOG.md`，做完一期接着下一期；教训在 `LESSONS.md`；每一步的状态在 `~/.agentq2/orders/<编号>/`。

## 谁干什么

| 活 | 模型 | 为什么 |
|---|---|---|
| 产品经理、难的模块、合到一起、修测试和审计的 bug | Opus | 想错一步全白做 |
| Opus 修 3 次还红，出手一次 | Fable | 最强也最贵，只用在别人都不行的时候 |
| 普通模块、Telegram 对话 | Sonnet | 接口和验收都写好了，照着做够快够省 |
| 唯一一次审计 | Codex 最强模型，xhigh | 换一家看 |
| 打勾、早报、合并、跑测试 | 程序 | 不用模型的不用模型 |

模块难不难由产品经理标（`hard`）。

强度按“错了代价多大、有没有人兜底”定，最低中：

- `xhigh`：只有一次机会的。Codex 审计、Fable 出手。
- `high`：想错、写错要返工的。产品经理、写代码、修、解冲突。
- `medium`：照规矩做、错了马上看得出来的。听消息认项目、把没提交的收个尾。

## 模块

| 模块 | 只负责 |
|---|---|
| `order` | 一条需求的状态，存成一个 JSON |
| `claude` | 起一次 Claude 会话、续上、撞额度自己等 |
| `repo` | git worktree、合并、跑测试 |
| `flow` | 上面那条直线 |
| `todo` | 项目的待办：列、挑、打勾 |
| `codex` | 审计时问 Codex 一次 |
| `lock` | 文件锁 |
| `tell` | 给你发消息、收你的消息 |
| `main.go`、`install.go` | 命令；装卸后台服务和派活技能 |

`flow` 用其余几个，其余几个只用 `lock`。

选型（语言、数据库、网页库、界面）和模块化的规范写在 `internal/flow/standards.md`，产品经理照它定，写进方案的「技术选型」一节。已有项目沿用它现在的。

## 守住小

- 产品代码不超过 2,650 行，`TestSmall` 卡着。要加东西先删东西。
- 没有队列、名额、范围、轮数、门、评测、自我进化、巡逻、夜班、建议编号。
- 待办留着：`agentq todo all` 把项目待办里能做的同时做，做完打勾，接着做被它挡着的。不说就不动，不自己挑。
- 早报留着：每天 8 点一条，卡住的、做好的、各项目用了多少 token。
- 每条需求一个独立进程，从头做到尾。被杀、重启过，`agentq resume`（launchd 每 5 分钟）从存下的那一步接着做。
- 额度撞上限，会话自己睡到重置再接着做。

## 给别人用（2026-11-26）

- **数据目录是 `~/.agentq2`**（`AGENTQ_HOME` 能换）。`~/.agentq` 是旧版的，结构完全不同；分开放才能并存、退得回去。
- **Telegram 密钥在 `<数据目录>/telegram.env`**，没有就用旧版写好的 `~/.agentq/secrets/telegram.env`。数据目录换掉时不看旧路径：测试和试用不会发到真的 Telegram。没配就不装收消息的服务，装上只会一直报错重启。
- **派活技能不覆盖**。`agentq install` 只装 `dispatch` 一个，装过的原文记在数据目录：和记录一样的才换新、才卸，用户自己的、改过的、软链过去的都不碰，只说一句。
- **没找到 `claude` 当场报错**，不记需求；不然要重试四次才卡住。
- **`install.sh` 只放程序**，不替用户跑 `agentq install`：那会加服务和技能，还会把当时的 `AGENTQ_*` 写进服务，升级时替用户跑会丢设置。
- **`install.sh` 认旧版**：旧版的 `agentq update` 会取到它，所以下载之前先看有没有旧版的软链和服务，有就什么都不改、说清怎么换；下载到的也要是这一版才换上。Release 不放 `VERSION`，旧版就不会自动换成这个完全不同的程序。
- **没有配置文件**，只有环境变量。没有自动升级、签名公证、Linux、Windows。

## 留着的底线

- 每个模块在自己的 worktree 里做，主分支只收测试过了的成品。
- 付款、对外发布、删用户数据、改账号不自动做。
- 测试由程序跑、看退出码，不听模型说。
