# 派活

收到当前 BACKLOG 待办明确执行合同的进程（通常带 `AGENTQ_JOB`）应使用 `agent-task` 亲自完成，不用本技能重新派发同一任务。

本技能只负责判断要不要交后台、把需求写清并启动，不在当前会话等待开发完成。用户/项目层保存项目别名、权限和通知偏好；通用技能不写死个人项目、账号或渠道。

下面的 `agentq` 找不到时都用 `$HOME/.local/bin/agentq`：桌面会话不一定读到新的 PATH。整个过程不让用户敲 agentq 命令，都由你跑。

## 0. 判断：当场做还是交后台

用户不用说触发词，由你判断。默认交后台：用户装 agentq 就是要说完需求去等结果。

- **交后台**：加功能、加命令、修 bug、改界面、做新项目，要写代码的需求都算，哪怕看起来几分钟就能写完。一句话里有多件事时拆开判断。
- **当场做**：只是提问（解释代码、出主意、查原因）；不加新行为的零碎改动（改错字、改文案、改一个配置值）；用户说「直接改」「我看着」「当场做」。正常回答或动手，不走下面的步骤。

拿不准时按交后台处理，并在回答里说一句「这条交给后台做了，要当场做就说一声」。

## 1. 后台能不能接活

跑 `agentq start --check`（只读）。第一行是状态，第二行是 `projects_root: <路径>`，后面是说明：

| 第一行 | 做法 |
|---|---|
| `ready` | 往下走 |
| `not-running` | 服务没在跑（被卸、重启后没加载、装的时候 CLI 还没弄好）：直接跑 `agentq start`，不问；失败就把输出给用户，这次条目照写、不 run |
| `paused` | 用户自己暂停的，不替用户打开。照写条目，第 5 节照常 `agentq run` 这一条（明确交代的活），回答里说一句自动调度暂停着、恢复说一声就行 |
| `off` | 安装时选了先不跑，或老安装从没开过：照写条目，不 run，告诉用户后台没开、说「开后台」就开。用户说开，再跑 `agentq start --accept-bypass` |
| `need-cli` | 官方 CLI 没装或没登录：照写条目，把说明里的命令给用户，让用户在终端弄好；弄好后用户再说一句，你重查 |
| `skills-only` | 把说明给用户，不派 |
| 命令失败或找不到 agentq | 把输出原样告诉用户，这次按当场做处理 |

同一个会话里拿到过 `ready`，后面的派活不用再查。

## 2. 识别项目

- 用户点名了别的项目：运行 `agentq projects`（每行目录名和路径；第三列写着 `exclude_projects` 的，用户没点名不派），按目录名和各项目 `AGENTS.md` 的说明匹配；不能唯一匹配就列候选问一次，不凭个人别名猜。
- 否则就是当前目录，不管它在不在 projects_root 下、是不是 Git 仓库、有没有 BACKLOG：第 3 节的 `agentq add` 会自己接入（不是 Git 仓库就 `git init` 并把现有文件做初始提交，补 BACKLOG 等文件，不在 projects_root 下的登记到 `extra_projects`），不问用户。
- 当前目录不像一个项目时问一句再动：家目录、桌面、下载、文档这类放杂物的目录，空的临时目录（如 `/tmp` 下）。问项目叫什么、放哪，带默认答案，例如「项目叫 hello-cli，放 `<projects_root>/hello-cli`，行吗？」。用户回「行」「随便」或只给名字就按默认：`mkdir -p` 建目录，在那里运行 `agentq add`。
- 项目不存在且需求是从零做一个新产品：加载 `new-project`。

## 3. 写入 BACKLOG

1. 在项目目录里用 `agentq add "<条目正文，不带 - [ ]>"` 写（超过 800 字时把细节写进文件，条目写路径）。它会接入项目、判断检查命令写 `.agentq/verify`、只提交 BACKLOG。已有等价任务文件则沿用，不并建一套。
2. 一项需求一条：

   ```text
   标题 —— 要什么；验收：可观察结果和验证方式；范围：已知页面/文件；理解成：……；不是：……
   ```

3. 条目依据方案的，写方案路径和节名，如「按 `docs/specs/<方案文件>.md`「页面结构」第 2 节」：审查门会读写了路径的方案，照方案做的设计不当问题提。
4. 条目保存产品目标、验收和授权范围；本次入口会话不直接实现、不等待后台等派活步骤不写成后台任务的禁止实现指令。
5. 用户一句话包含多个可独立验收目标时拆开；有顺序或前置条件时写清。能确定改动范围就在行尾写 `（范围：internal/gate/, docs/）`（路径前缀，逗号或顿号分隔），同项目范围互不重叠的条目才会并行，没写的一次一条；必须等另一条先合并的写 `（依赖：<那条标题里的一段字>）`，可写多个。只用这两种括号写法，正文里的「范围：」不算标记。
6. 验收后的意见写成 `验收 <原条目标题> 的意见`；修复近期已合并改动时记录对应提交号，供质量统计使用。
7. 用户回复「等用户决定」的条目时，把决定和原分支写回该条目，再移到「待做」顶部。
8. 写条目前跑 `agentq evolve constraints <项目目录名>`：列出的是这个项目被门拦过、确认过的事；和这次需求相关的写进验收（例如「验收：… 且不再出现 测试门：…」），无关的不写。命令不存在或没有约束就照常写。

## 4. 大方向：问一次，细节不问

设计、界面方向、前后端选型这类没定的事，交给后台之前在当前会话问用户一次。细节不问，开发交给模型。

- 最多一次、不超过 3 个问题，每个带默认答案；有界面的附 2 到 3 个方向描述让用户选。一条消息问完，不来回追问。
- 用户回「随便」或不回，就按默认。
- 把结果写在条目行尾：`（方向：用户定：纸墨风，Go 后端）`，或 `（方向：按默认：简洁，Go 后端）`，只用这个写法，括号里不再放全角括号。写了这个标记后台不会再问，任务合同和审查门都从条目看到。
- 用户没空答、又想让他后面在 Telegram 上定：条目标题结尾写 `（大方向）`，不写方向，不用 `agentq run`，由 tick 开工前问。
- 项目要从零新建时走 `agentq new --direction "<方向>" "<一句话>"`；用户说随便就写 `--direction "随便"`。配置 `discuss_enabled` 关着时不问。

## 5. 交给后台

- 用户说「夜里做」或「只加到待办」：写入后停止，留给定时调度。
- 其他：对每条执行 `agentq run <项目目录名> <标题关键词>`，只等命令返回启动结果，不等开发完成。第 1 节是 `off`、`need-cli` 时不 run。
- 并发已满或额度冷却时，保留条目，由后续调度接手；不要绕过限制。

## 6. 在对话里看进度、验收、停

用户不用敲命令，这些都在对话里说，你替用户跑：

- 「做得怎样」「进度」：`agentq status`，再按需 `agentq logs <任务ID>`；用一两句话说哪条在做、做了多久、哪条做完合进去了、哪条卡住和原因。
- 「验收」「做完的怎么看」：读项目 `docs/BACKLOG.md`「已完成」里那一条（带合并提交）和 `PROGRESS.md`，告诉用户去哪看、怎么试；用户试了提意见，按第 3 节第 6 条写成验收意见再派。
- 「停」「别做了」：停一条用 `agentq stop <任务ID>`（不知道 ID 先 `agentq status`）；全部先停下用 `agentq pause`，说清已在跑的会做完收尾，`agentq resume` 恢复。
- 「开后台」：按第 1 节重查，`off` 时跑 `agentq start --accept-bypass`，`paused` 时跑 `agentq resume`。
- 门卡住、要用户拍板的（`agentq gate report <任务ID>` 能看到原因）：把原因和选项讲给用户，用户定了再跑对应的 `agentq gate pass|rerun|abandon`，放行要写用户给的原因。

## 7. 回答

每条一行：交给后台了没有、任务 ID（如有）、做完按什么验收、想看进度怎么说（「问我做得怎样就行」）。没接入的项目说一句已经接入；后台是你拉起来的说一句。不要宣称尚未完成的结果，也不要因为派活而扩大远程推送、发布或付费授权。
